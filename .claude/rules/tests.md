# Тесты backend (источник: realization.md этап 12, quality.md)

- Настоящие PostgreSQL, Redis и S3-хранилище через testcontainers; схема создаётся миграциями. SQLite не использовать. Моки — только для внешних систем (Telegram) и имитации сбоев.
- Тест проверяет поведение, а не реализацию; имя говорит, что именно проверяется («повторная подписка не меняет счётчик»). Структура: подготовка, действие, проверка. Тесты независимы и проходят в любом порядке.
- Данные — через фабрики. Медленные тесты (FFmpeg, e2e) помечены маркером `slow`.
- Для каждой функции: основной сценарий, ошибки, права доступа (другой пользователь, гость, чужой приватный объект → 404), повторный запрос (идемпотентность).
- Конкурентность: счётчики реакций и подписок, перемещения в плейлисте проверяются параллельными запросами (`asyncio.gather`), итог сверяется с реальными строками.
- Число SQL-запросов на ключевых endpoint-ах (комментарии, ленты) проверяется счётчиком запросов в сессии: оно не растёт с числом элементов.
- Тестовые видео генерирует FFmpeg в фикстуре (синтетическая картинка и тон): горизонтальное, вертикальное, с поворотом, без звука, 60 кадров в секунду, очень короткое. Повреждённый файл и не-видео с расширением `.mp4` — тоже фикстуры. Бинарные файлы в Git не добавлять.
- Ожидание фоновой обработки — опрос с таймаутом, а не `sleep`.
- Каждый исправленный баг сначала воспроизводится тестом.
- Worker-тесты: повтор после временной ошибки (попытка 2), исчерпание попыток, двойная доставка, восстановление зависшей задачи, удаление видео во время обработки, повторный запуск не меняет результат.
