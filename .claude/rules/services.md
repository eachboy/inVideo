# Сервисный слой (источник: architecture.md 3.4, quality.md)

- Сервис содержит правила, проверку прав (функции политик в `policies.py`), оркестрацию репозиториев и адаптеров, границы транзакции. HTTP он не знает: бросает доменные исключения.
- Сессия БД одна на запрос; `commit` вызывает сервис в конце бизнес-операции, репозиторий не коммитит.
- Задачи Celery копятся в списке и отправляются **после успешного коммита**. Отправка до коммита — баг.
- Внутри открытой транзакции нет вызовов S3, Redis-блокировок и HTTP: сначала внешняя операция, затем короткая транзакция.
- Сложные правила — чистыми функциями без ввода-вывода (переходы статусов, лесенка качеств, оценка рекомендаций, дедупликация просмотров) с unit-тестами. Недопустимый переход статуса — ошибка программы.
- Сервис зависит от адаптеров (storage, cache, queue, telegram), а не от boto3 или Redis напрямую.
- Модуль A обращается к модулю B только через сервис B (например, `comments` проверяет доступ к видео через сервис `videos`). Циклов между модулями нет.
- Блокирующие операции в async-коде (argon2, Pillow, вызовы boto3 кроме генерации presigned URL) — в пуле потоков.
- Побочные эффекты (уведомления, счётчики канала) выполняются только транзакцией, которая реально сменила состояние, — тогда повтор не создаёт дублей.
- Нарушение уникальности из БД превращается в понятное доменное исключение (`HANDLE_TAKEN`).
