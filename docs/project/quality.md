# Часть VIII. Требования к качеству

Качество проекта для собеседования определяется не числом функций, а тем, насколько уверенно код выглядит изнутри: типы, тесты, понятные границы, история коммитов и умение объяснить решения. Ниже — стандарты, которые проверяются автоматически в CI, и чек-лист для самопроверки.

## Стандарты кода

### Type Hints

- Аннотации у всех функций, методов и атрибутов классов, включая возвращаемые значения.
- mypy в строгом режиме для пакета приложения с первого дня — включить строгость сразу проще, чем потом исправлять сотни ошибок.
- Any в публичных функциях запрещён; для словарей с известной формой — TypedDict или Pydantic-модель; для зависимостей от внешних систем — Protocol.
- Перечисления статусов, видимостей, ролей — enum-классы, а не строки по коду.

### Pydantic Validation

- Отдельные схемы на вход и на выход; входные запрещают лишние поля.
- Ограничения прямо в типах: длины, диапазоны, шаблоны, перечисления.
- Выходные схемы — всегда через response\_model, чтобы наружу не утекло лишнее.
- Настройки приложения — тоже Pydantic: при запуске с некорректной конфигурацией приложение падает сразу с понятной ошибкой, а не через час на первом запросе.

### SQLAlchemy 2.0

- Только современный стиль: типизированные модели, запросы через конструктор select, никакого устаревшего Query API.
- Явная стратегия подгрузки связей в каждом запросе; неявная ленивая подгрузка запрещена на уровне моделей.
- Сессия на запрос; коммит — в сервисе; объекты не устаревают после коммита в async-режиме.
- Запросы — только в репозиториях.

### Alembic Migrations

- Одна миграция — одно логическое изменение, понятное название.
- Автогенерация — только черновик: каждую миграцию читать и править руками (индексы, триггеры, расширения автогенерация не видит или видит неточно).
- Применённые миграции не редактируются никогда — только новая миграция.
- У каждой миграции есть откат; CI проверяет «применить всё → откатить всё → применить всё» и что автогенерация на текущих моделях пуста (модели и база не разошлись).
- Изменения данных — отдельные миграции, не смешиваются с изменением схемы.
- Изменения обратно совместимы на время деплоя: сначала добавить колонку, выкатить код, потом удалить старую.

### Pytest

- Тест проверяет поведение, а не реализацию; название говорит, что именно (например, «повторная подписка не меняет счётчик»).
- Структура «подготовка — действие — проверка»; тесты независимы и проходят в любом порядке.
- Настоящие PostgreSQL, Redis и хранилище в контейнерах; моки — только для внешних систем (Telegram) и для имитации сбоев.
- Фабрики данных вместо ручного создания объектов.
- Маркеры для медленных тестов (FFmpeg, e2e), чтобы локально можно было запускать быстрый набор.
- Каждый исправленный баг сначала воспроизводится тестом.

### Structured Logging

- Логи в JSON в stdout. Обязательные поля: время, уровень, событие (короткий постоянный идентификатор, а не фраза с подставленными значениями), request\_id, user\_id; в пайплайне — video\_id, job\_id, этап, длительность.
- request\_id передаётся из API в задачу Celery через её заголовки — логи запроса и связанной обработки находятся одним поиском.
- Уровни: DEBUG — только локально; INFO — бизнес-события (видео загружено, обработано); WARNING — ожидаемые сбои (повтор задачи); ERROR — то, что требует внимания человека.
- Пароли, токены, подписи, заголовок Authorization маскируются автоматически.

### Environment Variables

- Вся конфигурация — переменные окружения (принцип 12-factor app); код одинаков во всех окружениях.
- Значения по умолчанию — только безопасные и только для разработки; в продакшене обязательные переменные без значения роняют запуск.
- .env.example документирует каждую переменную.

## Архитектурные принципы

### Clean Architecture там, где она оправдана

Используется: слои API → сервис → репозиторий; бизнес-логика не знает про HTTP; чистые функции без ввода-вывода для сложных правил (переходы статусов, лесенка, формула рекомендаций) — их легко тестировать. Не используется: полная гексагональная архитектура с портами и адаптерами для каждой мелочи, отдельные доменные сущности поверх ORM-моделей, use case-класс на каждый endpoint. Для проекта одного разработчика это утроит объём кода без пользы.

### SOLID без избыточной абстракции

- **Единственная ответственность:** роутер — HTTP, сервис — правила, репозиторий — запросы, задача — точка входа фоновой работы.
- **Инверсия зависимостей:** сервисы зависят от адаптеров хранилища, кеша, очереди и Telegram — их подменяют в тестах.
- **Без абстракции ради абстракции:** интерфейс с единственной реализацией оправдан только для внешней системы. Универсальный базовый репозиторий, фабрики фабрик, слои «на будущее» — не нужны. Правило трёх повторений: обобщать код, когда он повторился третий раз, а не раньше.

### Dependency Injection

Встроенный Depends в FastAPI: настройки, сессия, текущий пользователь, сервисы. Никаких глобальных объектов с состоянием, к которым код обращается напрямую. Каждая зависимость подменяется в тестах.

## Процесс

### Git workflow

- Ветка main всегда рабочая и защищена; изменения — через короткие ветки (1–3 дня работы) и pull request, даже без ревьюера: PR — это описание изменения и прогон CI.
- Названия веток по типу: feature, fix, chore с кратким описанием.
- Сообщения коммитов по Conventional Commits (feat, fix, refactor, test, docs, chore); при слиянии PR коммиты объединяются в один осмысленный.
- Задачи этапов из Части V — issues в GitHub с меткой этапа и доской проекта; PR ссылается на issue.
- Релизы помечаются тегами по семантическому версионированию; изменения описываются в CHANGELOG.

### Code Review checklist

Перед слиянием каждого PR — самопроверка по списку:

- [ ] Изменение делает одну вещь; PR читается за 15 минут.
- [ ] Есть тесты на основной сценарий и на ошибки; CI зелёный.
- [ ] Проверены права доступа: может ли другой пользователь вызвать это для чужого объекта?
- [ ] Нет утечки приватных данных в ответах, поиске, лентах и кешах.
- [ ] Пользовательский ввод валидируется; сортировки и фильтры — из перечислений.
- [ ] Нет запросов в цикле (N+1); новые запросы проверены через EXPLAIN, нужные индексы добавлены.
- [ ] Нет сетевых вызовов внутри открытой транзакции; задачи ставятся после коммита.
- [ ] Операция идемпотентна или защищена от повторного запроса.
- [ ] Миграция прочитана, есть откат, она обратно совместима.
- [ ] Ошибки возвращаются в едином формате с осмысленным кодом.
- [ ] Логи содержат нужный контекст и не содержат секретов.
- [ ] Новые переменные окружения добавлены в .env.example.
- [ ] Документация и ADR обновлены, если изменилось архитектурное решение.

### CI/CD — автоматические барьеры качества

| Проверка | Что ловит |
| --- | --- |
| Ruff (линтер и проверка форматирования) | Стиль, ошибки, неиспользуемый код |
| mypy | Ошибки типов |
| ESLint, Prettier, проверка типов TypeScript | То же для фронтенда |
| pytest с порогом покрытия | Регрессии |
| Проверка миграций (применение, откат, пустая автогенерация) | Расхождение моделей и схемы |
| Генерация типов из OpenAPI | Расхождение контракта backend и фронтенда |
| pip-audit и npm audit | Уязвимые зависимости |
| Сборка Docker-образов | Сломанная сборка |
| E2E на Compose (для PR в main) | Поломка сценариев целиком |

## Как выглядит результат, который не стыдно показать

**Репозиторий:**

- README как витрина: одна фраза о проекте, GIF или видео с демонстрацией (загрузка → обработка → просмотр), схема архитектуры, стек, ключевые решения с аргументами, запуск одной командой, ссылка на работающее демо, бейджи CI и покрытия.
- Папка с ADR — 6–10 коротких записей о решениях и компромиссах.
- Чистая история коммитов и PR, по которой видна последовательная работа.
- Тесты, которые реально проверяют сложные места: гонки, повторы, права доступа.

**Работающий продукт:**

- Демо на домене по HTTPS с несколькими загруженными видео и тестовым аккаунтом.
- Дашборд Grafana (скриншот в README).

**Готовность к разговору.** Уметь за 2–3 минуты объяснить каждую из этих тем:

1. Почему видео не загружается через FastAPI и как работает multipart с докачкой.
2. Как устроена обработка: очередь, захват задачи, идемпотентность, повторы, что будет при падении воркера.
3. Как работает HLS и адаптивный битрейт, почему ключевые кадры должны быть выровнены.
4. Как защищены приватные видео без участия Python в раздаче сегментов.
5. Почему access-токен короткий, а refresh — в httpOnly-cookie с ротацией.
6. Как просмотры считаются без накрутки и без записи в базу на каждое событие.
7. Почему модульный монолит, а не микросервисы, и где он разрежется при росте.
8. Что вы сделали бы иначе и что улучшили бы дальше.

Последний пункт важнее, чем кажется: честный ответ о компромиссах и слабых местах убеждает интервьюера сильнее, чем список технологий.
