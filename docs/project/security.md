# Часть VII. Безопасность и производительность

Главные риски inVideo — не классические веб-уязвимости (от них во многом защищают FastAPI, SQLAlchemy и React), а специфичные для видео: недоверенные файлы, которые разбирает FFmpeg, утечка приватных видео через раздачу и кеши, исчерпание диска и CPU. Каждый пункт ниже — риск, как он возникает, как его предотвратить и на каком этапе это сделать.

## Безопасность

### Безопасность загрузки файлов

- **Риск:** перегрузка API, заполнение диска, загрузка чужого контента в чужое видео, выполнение загруженного файла.
- **Как возникает:** файлы идут через API; ключи объектов строятся из имени файла; права на загрузку не проверяются при подписи каждой части.
- **Как предотвратить:** прямая загрузка в хранилище по presigned URL с коротким сроком жизни; права проверяются на каждой операции (инициализация, подпись, завершение); ключи объектов генерирует сервер; оригиналы лежат в приватном бакете и никогда не отдаются пользователям; брошенные загрузки удаляются.
- **Этап:** 5.

### Ограничение размеров файлов

- **Риск:** заполнение хранилища, долгая и дорогая обработка, отказ в обслуживании.
- **Как возникает:** размер проверяется только на клиенте или только при инициализации, а клиент загружает больше заявленного.
- **Как предотвратить:** лимит при инициализации; размер и MD5 каждой части в подписи — хранилище не примет большую часть; число частей ограничено; при завершении итоговый размер сверяется с заявленным. Квоты на пользователя по числу одновременных загрузок и объёму в сутки. Для аватаров — лимит тела в Nginx и потоковое чтение в FastAPI. Лимиты длительности и разрешения — в пайплайне.
- **Этап:** 4 (изображения), 5 (видео), 6 (длительность и разрешение).

### Проверка реального формата файлов

- **Риск:** под видом видео загружается HTML, скрипт, архив или специально сформированный файл.
- **Как возникает:** доверие расширению и Content-Type, которые полностью контролирует клиент.
- **Как предотвратить:** формат видео определяет FFprobe по содержимому; разрешён ограниченный список контейнеров и кодеков; изображения открываются Pillow с проверкой реального формата. Конечный результат всегда **перекодирован** — пользователи получают только то, что создал ваш FFmpeg, а не исходные байты.
- **Этап:** 4, 6.

### Защита от вредоносных файлов

- **Риск:** эксплуатация уязвимостей в декодерах FFmpeg или Pillow; SSRF через FFmpeg; «бомбы» — картинка 50000×50000 или видео с огромным числом кадров.
- **Как возникает:** FFmpeg поддерживает сотни форматов и протоколов, включая сетевые и плейлисты, которые сами ссылаются на другие файлы и URL.
- **Как предотвратить:** белый список протоколов FFmpeg — только локальный файл; ограничение числа пикселей в Pillow; лимиты длительности, разрешения и частоты кадров после FFprobe; таймауты процессов; актуальная версия FFmpeg с исправлениями безопасности (обновление образа воркера раз в месяц); изоляция (следующий пункт). Антивирус для видео не обязателен.
- **Этап:** 6.

### Изоляция FFmpeg Workers

- **Риск:** если уязвимость FFmpeg всё же сработает, злоумышленник получает процесс внутри вашей инфраструктуры.
- **Как возникает:** воркер работает от root, имеет доступ в интернет, к секретам и ко всем сервисам.
- **Как предотвратить:** отдельный контейнер воркера; непривилегированный пользователь; удалены все Linux capabilities и запрещено повышение привилегий; корневая файловая система только для чтения, запись — только в выделенный том для временных файлов; воркер подключён только к внутренней сети Docker без выхода в интернет; у воркера свои ключи хранилища с минимальными правами (читать оригиналы, писать в hls и images) и своя роль в PostgreSQL; FFmpeg запускается списком аргументов, без shell.
- **Этап:** 6 (базовая изоляция), 13 (ужесточение).

### Ограничение CPU и RAM

- **Риск:** транскодирование забирает все ядра и память — сайт перестаёт отвечать, OOM-killer убивает базу данных.
- **Как возникает:** несколько FFmpeg параллельно без лимитов на одном сервере с API и PostgreSQL.
- **Как предотвратить:** лимиты CPU и памяти контейнера worker-video (оставить минимум одно ядро и 1–2 ГБ остальным сервисам); параллелизм воркера 1; потоки FFmpeg по числу выделенных ядер; пониженный приоритет процесса; мягкий и жёсткий лимиты времени задачи; перезапуск процесса воркера после N задач; проверка свободного места перед стартом; лимиты памяти и для остальных контейнеров, чтобы OOM затрагивал виновника, а не базу.
- **Этап:** 6.

### JWT Security

- **Риск:** подделка токена, кража токена, невозможность отозвать доступ.
- **Как возникает:** алгоритм берётся из заголовка токена (атака «alg: none» или подмена алгоритма); слабый секрет; долгоживущий access-токен; токен в localStorage, откуда его читает любой XSS.
- **Как предотвратить:** фиксированный список разрешённых алгоритмов (HS256) при проверке; случайный секрет не короче 256 бит из переменной окружения; проверка срока, типа и обязательных полей; access-токен 15 минут, только в памяти; refresh-токен непрозрачный, в httpOnly-cookie, хранится в базе хешем, ротируется с обнаружением повторного использования; список отозванных сессий в Redis; в токене нет персональных данных; идентификатор ключа в заголовке токена для будущей ротации секрета.
- **Этап:** 3.

### Rate Limiting

- **Риск:** перебор паролей, спам комментариями, накрутка просмотров, исчерпание ресурсов дорогими запросами (поиск, инициализация загрузок).
- **Как возникает:** endpoint-ы без ограничений частоты.
- **Как предотвратить:** два уровня. Nginx — грубые лимиты по IP на /api и особенно на /api/v1/auth, плюс лимит одновременных соединений. Приложение — Redis-счётчики со скользящим окном по пользователю и по IP для чувствительных действий: вход, регистрация, комментарии, реакции, инициализация загрузки, событие просмотра, поиск. Ответ 429 с Retry-After. Реальный IP клиента берётся только из заголовка, который выставляет ваш Nginx; заголовкам от клиента доверять нельзя — их легко подделать.
- **Этап:** 3 (auth), 8 (социальные функции), 13 (Nginx в продакшене).

### SQL Injection

- **Риск:** чтение и изменение любых данных базы.
- **Как возникает:** SQL собирается конкатенацией или f-строками с пользовательским вводом; пользовательская строка подставляется в ORDER BY или имя колонки.
- **Как предотвратить:** только запросы SQLAlchemy и параметризованные текстовые запросы; сортировка и фильтры — из закрытых перечислений, которые отображаются на заранее заданные выражения; экранирование спецсимволов шаблонов (процент и подчёркивание) при поиске по подстроке; приложение подключается к базе пользователем без прав на изменение схемы, миграции выполняются отдельным пользователем.
- **Этап:** с этапа 2 — как правило для всего кода.

### XSS

- **Риск:** выполнение чужого JavaScript в браузере пользователя: кража access-токена из памяти, действия от его имени.
- **Как возникает:** вывод пользовательского текста как HTML; ссылки с javascript: в href; SVG-аватары со встроенным скриптом; неверный Content-Type у пользовательских файлов.
- **Как предотвратить:** React экранирует вывод по умолчанию — никогда не вставлять пользовательский текст как HTML; ссылки в описаниях и комментариях распознаются безопасно и допускают только http и https; SVG не принимается, все изображения перекодируются в WebP; строгий Content-Security-Policy (скрипты только со своего домена, без inline); заголовок, запрещающий браузеру угадывать тип содержимого.
- **Этап:** 4 (изображения), 8 (комментарии), 13 (CSP и заголовки).

### CSRF

- **Риск:** чужой сайт заставляет браузер пользователя выполнить действие в inVideo.
- **Как возникает:** авторизация на основе cookie, которые браузер прикладывает к запросам с других сайтов.
- **Как предотвратить:** основная авторизация — access-токен в заголовке Authorization, который браузер сам не прикладывает, поэтому обычные endpoint-ы к CSRF не уязвимы. Единственные endpoint-ы с cookie — обновление токена и выход: их cookie имеет SameSite=Strict и ограниченный путь, а сервер дополнительно проверяет заголовок Origin. Cookie доступа к HLS даёт только чтение.
- **Этап:** 3.

### CORS

- **Риск:** чужой сайт читает ответы API от имени пользователя.
- **Как возникает:** разрешение любого origin, особенно вместе с передачей cookie.
- **Как предотвратить:** фронтенд и API на одном домене (через Nginx) — CORS для API не нужен вовсе и выключен. CORS настраивается только на бакете для загрузки частей: разрешён только origin фронтенда, только нужные методы, открыт заголовок ETag. Звёздочка не используется.
- **Этап:** 1 (один origin), 5 (бакет).

### Защита приватных видео

- **Риск:** посторонний смотрит приватное видео или узнаёт о его существовании.
- **Как возникает:** проверка прав только на странице видео, а сегменты доступны по прямой ссылке; приватные видео попадают в поиск, ленты, рекомендации или общий кеш; обложки приватных видео лежат в публичном месте.
- **Как предотвратить:** политика доступа в сервисе для каждого чтения; чужие приватные объекты — 404; подписанная cookie для всех HLS-путей, проверка в Nginx до обращения к кешу; неугадываемые идентификаторы; условие видимости в каждом запросе поиска, лент и рекомендаций и в условиях частичных индексов; общий Redis-кеш только для публичных данных; обложки приватных видео отдаются по защищённому пути; сброс кешей при смене видимости; оригиналы не отдаются никогда.
- **Этап:** 7 (раздача), 8–9 (ленты и поиск).

### Безопасное хранение секретов

- **Риск:** утечка паролей базы, ключей хранилища, секрета JWT, токена бота.
- **Как возникает:** .env в Git; секреты в Dockerfile или аргументах сборки (остаются в слоях образа); секреты в логах.
- **Как предотвратить:** конфигурация только через переменные окружения; .env в .gitignore, в репозитории только .env.example с заглушками; на сервере файл с правами только для владельца; в CI — секреты GitHub Actions; сканер секретов в pre-commit; в логах — процессор structlog, маскирующий поля с паролями, токенами, заголовком Authorization и подписями; разные секреты для каждого окружения; процедура ротации.
- **Этап:** 1 (основа), 13 (продакшен).

### Защита MinIO

- **Риск:** чтение или удаление всех видео, подмена файлов.
- **Как возникает:** root-ключи используются приложением; бакеты с публичным чтением открыты в интернет; веб-консоль доступна снаружи.
- **Как предотвратить:** root-ключи — только для скрипта инициализации; у API и воркера отдельные ключи с политиками на конкретные бакеты и действия; хранилище не публикуется наружу, кроме поддомена загрузок, где Nginx пропускает только методы multipart-загрузки; консоль недоступна извне; анонимное чтение бакета HLS возможно только из внутренней сети, где к нему ходит Nginx.
- **Этап:** 5, 13.

### Nginx Security

- **Риск:** перехват трафика, медленные атаки, раскрытие версий, кликджекинг.
- **Как возникает:** HTTP без TLS, настройки по умолчанию.
- **Как предотвратить:** только TLS 1.2 и 1.3; редирект на HTTPS и HSTS; скрытие версии; заголовки безопасности (CSP, запрет встраивания во фреймы, Referrer-Policy, запрет угадывания типа); маленький лимит тела по умолчанию и увеличенный только там, где нужно; таймауты чтения заголовков и тела против медленных атак; лимит соединений с IP; запрет скрытых файлов; правильная передача реального IP; в логах поддомена загрузок не пишется строка запроса (там подписи presigned URL).
- **Этап:** 7 (базово), 13 (полностью).

## Производительность

### Оптимизация PostgreSQL

- **Риск:** медленные ответы, исчерпание соединений, блокировки.
- **Как возникает:** большие пулы соединений в каждом процессе; долгие транзакции; сетевые вызовы к хранилищу внутри открытой транзакции; отсутствие таймаутов.
- **Как предотвратить:** суммарный размер пулов всех процессов (API и воркеры) меньше лимита соединений базы; таймаут выполнения запроса для роли приложения (например, 5 секунд) и таймаут простоя в транзакции; **никаких обращений к S3, Redis-блокировок и HTTP внутри открытой транзакции** — сначала внешняя операция, затем короткая транзакция; базовая настройка памяти под размер сервера; расширение pg\_stat\_statements для поиска медленных запросов; внимание к autovacuum на часто изменяемых таблицах (video\_views, watch\_history). PgBouncer — только если соединений станет не хватать.
- **Этап:** 2 (пулы, таймауты), 13 (настройка сервера).

### Индексы

- **Риск:** полное сканирование больших таблиц или, наоборот, лишние индексы, замедляющие запись.
- **Как возникает:** индексы создаются «на всякий случай» или не создаются вовсе; порядок колонок составного индекса не совпадает с фильтром и сортировкой.
- **Как предотвратить:** индекс проектируется под конкретный запрос: сначала колонки равенства, затем колонка сортировки; частичные индексы для «горячих» подмножеств (публичные готовые видео, активные сессии); проверка каждого нового запроса через EXPLAIN ANALYZE на сгенерированных данных; периодический поиск неиспользуемых индексов по статистике PostgreSQL.
- **Этап:** каждый этап, где появляются запросы; массовая проверка — этап 9.

### N+1 queries

- **Риск:** страница из 20 комментариев делает 21 запрос, лента из 50 видео — 101.
- **Как возникает:** ленивая подгрузка связей ORM при обращении к атрибуту в цикле или при сериализации.
- **Как предотвратить:** явная стратегия подгрузки в каждом запросе репозитория (JOIN для «один к одному», пакетная подгрузка для коллекций); у связей моделей режим, который **запрещает** неявную ленивую подгрузку и бросает ошибку — в async SQLAlchemy она всё равно не работает, а так ошибка видна сразу; тесты, считающие число SQL-запросов на ключевых endpoint-ах.
- **Этап:** 2 (настройка моделей), 8 (комментарии, ленты).

### Кэширование

- **Риск:** без кеша — лишняя нагрузка на базу; с неправильным кешем — устаревшие или чужие данные.
- **Как возникает:** кеширование персональных данных под общим ключом; отсутствие инвалидации; одновременное истечение популярного ключа и лавина запросов в базу.
- **Как предотвратить:** паттерн cache-aside в Redis для: публичных метаданных видео (60 с), шапки канала (60 с), трендов, первой страницы популярных поисковых запросов, списков рекомендаций (30 мин), числа непрочитанных, статистики Studio (10 мин). Персональные данные — только под ключом пользователя или вне кеша. Инвалидация удалением ключа при изменении. Случайный разброс TTL против одновременного истечения. HTTP-кеш: статика фронтенда с хешем в имени — на год, index.html — без кеша.
- **Этап:** 8, 9.

### Оптимизация HLS Streaming

- **Риск:** медленный старт воспроизведения, перегрузка хранилища, лишний трафик.
- **Как возникает:** каждый сегмент читается из хранилища; кеш не используется из-за меняющихся путей; лесенка без низких качеств.
- **Как предотвратить:** дисковый кеш Nginx с блокировкой от одновременных промахов; неизменяемые версионные пути и долгий Cache-Control; постоянные соединения Nginx с хранилищем; HTTP/2; эффективная отправка файлов ядром; сегменты 6 секунд — компромисс между числом запросов и скоростью переключения; старт с невысокого качества для быстрого начала; ограничение качества размером плеера; позже — CDN перед Nginx без изменений в приложении.
- **Этап:** 7.

### Ограничение нагрузки на фоновые задачи

- **Риск:** очередь растёт бесконечно, лёгкие задачи (уведомления) стоят за часовым транскодированием, один пользователь занимает все воркеры.
- **Как возникает:** все задачи в одной очереди; нет лимитов частоты и справедливости.
- **Как предотвратить:** отдельные очереди и отдельные воркеры для тяжёлых и лёгких задач; ограничение частоты для задач с внешними API (Telegram); пакетная обработка (сброс просмотров, массовые уведомления) вместо задачи на каждое событие; лимит одновременно обрабатываемых видео на одного пользователя (например, 2), остальные ждут в QUEUED — один автор с 50 роликами не блокирует остальных; ограниченное число повторов; мониторинг длины очередей с алертом.
- **Этап:** 6, 8, 13.
